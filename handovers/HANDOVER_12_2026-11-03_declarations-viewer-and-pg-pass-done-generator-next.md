## Traps and warnings

**Every first version failed review in S11, as in S09 and S10.** Two passes on sol, two FAILS, all findings applied.
Expect it for the generator note, and build the time in.

**Codex calls time out after 60 seconds, but keep running.** The tool reports "did not respond within 60s"; the
reviewer usually finishes within one to three minutes. Do not call it again: poll for the answer file with a loop of
`sleep 5` in one `device_bash` call. The brief that worked: "Read only one file: …", the standard stated, "assume an
experienced … rejects it", up to five findings with failure cases, `VERDICT:` line, answer written with apply_patch to
a named file under `scratch/`. Copy the object into `scratch/` first if it is not committed.

**The step timestamps ran ahead of the clock again** (S11-004 to S11-006, S11-008, S11-010). Take the time from the
shell immediately before writing each step and do not estimate forward.

**Records of rulings are not overhead.** AUD-S11-1 read the steps that write the author's rulings into ADRs and the
register as design work (build), as the rubric says: only coordination about the session itself or the step log is
overhead. Label them by what they are about.

**Moving files to the desktop.** As before: tarballs into `scratch/_transfer/`, extracted with `tar --overwrite`. After
each commit, `mv` any of `.git/HEAD.lock`, `.git/index.lock`, `.git/objects/maintenance.lock` to `.git/stale-...`.
Deletion in `C:\Git\business-intelligence` was approved for S11 only; a new session needs a new approval, which also
stops git leaving lock files behind. The connected-folder mount (`$HOME/mnt/business-intelligence`) is the one that
carries that approval; the same folder reached through `$HOME/mnt/Git/` does not.

**Name collisions in Python scripts.** In `build.py` a loop variable `a` overwrote the parsed arguments `a`; arguments
are now `args`. Watch for the same in the generator.

**`model_lib.catalogue()` is the one reader of catalogue evidence** for the viewer and the checker. It passes through
triggers, checks and view fields since S11; add fields there rather than reading the JSON a second way.

**The viewer is a reader, never a source of truth** (142 §3), and so would be any generated SQL: the declarations are
the truth, and generated files are never edited.

**The runner refuses Python models and dbt packages** (ADR-0015, ADR-0032). The generator runs outside it, by a person
or the agent layer, and must write plain SQL.

**PostgreSQL in the cloud workspace.** The server binaries are at `/usr/lib/postgresql/16/bin`; `initdb` refuses root,
so run it as the user `claude` in a folder that user owns (`/home/claude/pgtest` was used). DuckDB and dbt are not
installed in the cloud workspace; pip works there.
