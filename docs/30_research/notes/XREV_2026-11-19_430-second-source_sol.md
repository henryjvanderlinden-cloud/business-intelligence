## sol's answer, verbatim

1. **FAILS — Figures-only feedback is a split and key oracle (questions 1 and 3; 430 §5).** Proposals cover every CRM record, but development counts cover only the hidden development part. Compare two method versions whose output differs only by replacing one record's abstention with a link. A change in the reported proposed-link count identifies that record as development; no change identifies it as held back. For a development record, the change in the number of right links, recoverable from counts and precision, tests the proposed counterpart. Both versions can be genuine method changes: logging versions does not prevent this channel. The design acknowledges some development leakage but incorrectly treats the absence of per-customer verdicts as protection against recovering them. Independently assigning CRM records also permits two records of the same underlying entity to straddle the split. Feedback on the development duplicate then supplies an identity label useful for its held-back sibling. The conduct rule against probing does not prevent that transfer during ordinary tuning.

   **Minimal fix:** make development membership and its permitted feedback explicit rather than promising to hide what the counters disclose. Split connected identity groups, including duplicate and merged records and their WWI counterparts, together. Keep held-back labels inaccessible through development scoring. Precommit a bounded development evaluation schedule and candidate versions; arbitrary adaptive aggregate queries cannot also guarantee that development labels remain secret. If secrecy of development membership and labels remains a requirement, the feedback interface must change. The extract's prohibition on identifier-derived artefacts is a sound requirement, but the bundle contains no generator or output from which its implementation could be certified.

2. **FAILS — There is no frozen evaluation instance or unambiguous one-shot holdout (questions 3 and 5; 430 §§2, 5–7; 410's freeze guard).** A daily key and a seeded assignment do not specify a frozen sample or an invariant assignment across dates. A generator can deterministically assign the day's records using the seed and date, moving yesterday's held-back customer into today's development part while satisfying the stated per-day assignment rule. Even with stable assignments, development feedback on a later version of the same entity can inform an earlier held-back evaluation. New customers can silently change the test population after development starts. “Refuses it a second time” has no specified scope: per date permits repeated holdout evaluations on substantially the same customers; globally, the first cheap-signals file can consume the only evaluation before the model file is scored. An automatic confidence selected on development is legitimate, but only if its selection rule and final value are locked before any held-back result is returned.

   **Minimal fix:** freeze and privately identify an experiment before development: exact source snapshots, key, grouped split, scorer version and evaluation policy. Daily generation can continue, but later customers and keys must not enter that experiment. Bind every score request to it. Commit both final method files and their confidence cutoffs together, then release their held-back results in one operation. Persist consumption atomically before release, with idempotent recovery for the identical submission after a crash. A breach must retire that experiment, not merely regenerate its data under the same scoring history. Separate reporting of cheap signals holds as written; the freeze and hold-back guards do not, despite ADR-0044 repeating them.

3. **FAILS — Precision and recall do not each have one value (question 2; 430 §5).** Let CRM record r represent WWI customers a and b, and propose r→a. The proposal is right by the explicit merge rule. Recall is either 1/2 if “true links” means the two true record pairs, or 1 if it means CRM records with an acceptable counterpart. The singular proposal schema cannot achieve full pair recall on merges. Two duplicate CRM records both matching a yield two right links but only one recovered WWI entity; an entity-based denominator can therefore produce a different result again. Adding a CRM-only record and a WWI-only customer leaves unspecified whether either enters recall's denominator. A mixed-tier result also leaves open whether each tier's recall divides by all true links or only the truth associated with that tier. Duplicate-pair scoring does not define orientation, repeated pairs, transitive closure, or whether two merged records sharing just one constituent are “the same customer.” Empty predictions or abstentions give zero denominators, and confidence ties at rank 50 can change top-50 precision.

   **Minimal fix:** publish a complete scoring contract. Consistent with the existing one-target schema, use eligible CRM records with a nonempty acceptable-target set as the cross-source recall denominator; count a proposed link as correct precisely when its target belongs to that set. CRM duplicates then remain separate retrieval opportunities, CRM-only records test no-counterpart accuracy, and WWI-only records are outside this directional recall. Use that same denominator for both tiers and label the resulting recalls as contributions. Define the duplicate relation separately, including merge handling, canonical unordered pairs and rejection of duplicate submissions. Specify input validation, missing and invalid IDs, abstention semantics, empty-denominator results, top-50 ties and samples below 50. Reporting merges separately does not resolve any of these denominators.

4. **FAILS — The third threshold has no unique comparison, and empty tiers lack a verdict (question 2; 430 §6 and ADR-0044 decision 5).** Suppose the locked automatic tiers give cheap signals precision 1.00 and recall 0.40, and the model precision 0.98 and recall 0.46. Both satisfy the automatic precision floor. The model passes if “at the automatic tier's precision” means both meet 0.98; an exact equal-precision comparison is unavailable from these operating points and might fail if the model must reach 1.00. Discrete rankings need not contain any common precision, and interpolation, threshold searching and tie treatment are unspecified. Searching held-back results for a common operating point would also violate the one-shot evaluation. A method proposing no automatic links or no queue links leaves the first or second threshold undefined.

   **Minimal fix:** settle the interpretation before scoring and record any clarification of ADR-0044. One determinate rule is to select each method's cutoff on development under a fixed selection and tie policy, lock it, require both held-back automatic precisions to meet 0.98, and compare their recalls at those locked cutoffs. This measures recall at a common precision floor, not exact equal precision. Explicitly make an empty automatic tier or queue insufficient to demonstrate its respective threshold; report undefined metrics as such rather than converting them to successful precision values.

5. **FAILS — Atomic CRM publication does not make the extract/key pair recoverable, and independent retention can orphan it (question 4; 430 §§2 and 4).** A generator can publish a complete CRM folder and crash before writing its hidden key, or write a replacement key and crash before publishing the corresponding CRM folder. Both respect the specified atomic CRM-folder requirement; scoring by date alone can then use a missing or mismatched key. Retention has a concrete failure: after successful days 1–3, exports for days 4–6 succeed while CRM generation fails. WWI retains days 4–6; CRM's newest three successful folders remain days 1–3, whose WWI inputs have been deleted. “The next export runs it again” does not recover those dates. The runner can also observe the published WWI extract while CRM generation is pending. That is harmless for the current WWI-only runner, but cannot be treated as a paired-source readiness signal later.

   **Minimal fix:** give each generation immutable input, output and key identities and a final readiness record written only after all are durable; score only a verified matching generation. Record generator failure separately from the already committed advance/export, support retry of an available input without advancing, and define retention jointly with pending work and frozen experiments. Check available space on each destination volume before the added writes, bound temporary output and clean failed staging files; the existing WWI admission check does not cover these writes. Start the scheduled job only after its newly required Python environment and hidden-folder access are ready: setup currently enables it before installing Python. Keep proposals as validated data, invoke only pinned code, and sanitize scorer/generator failures before the existing exception-to-response/log path can expose hidden contents. The additional fixed action need not break one-request-per-run, and copying into the existing protected pin directory can preserve admin-only code; neither requires weakening those guarantees.

VERDICT: FAILS — the hidden evaluation is probeable, its scores are underdefined, and daily publication lacks a recoverable extract/key contract.
