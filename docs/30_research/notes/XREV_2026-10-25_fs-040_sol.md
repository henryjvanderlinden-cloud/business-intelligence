## Pass 1 — sol's answer, verbatim

## Findings

1. **Quoted sentence:** “camt.053 (statement) and camt.054 (debit/credit notification) have the structure Statement → Entry → Entry Details → Transaction Details.”

   **What is wrong:** This gives camt.054 a `Statement` container. In camt.054, entries are grouped under a notification, not a statement. It also omits camt.052 from a purported account-reporting reference: all three use closely related entry/detail structures, but their report containers differ.

   **Correction:** camt.052 is `BankToCustomerAccountReport → Report (Rpt) → Entry (Ntry) → EntryDetails (NtryDtls) → TransactionDetails (TxDtls)`; camt.053 is `BankToCustomerStatement → Statement (Stmt) → Ntry → NtryDtls → TxDtls`; camt.054 is `BankToCustomerDebitCreditNotification → Notification (Ntfctn) → Ntry → NtryDtls → TxDtls`. `NtryDtls` and `TxDtls` are repeatable/optional according to the applicable message version, so this is a hierarchy, not a guarantee that every entry contains transaction-level detail.

   **Confidence:** High.

2. **Quoted sentence:** “The Bank Transaction Code (`BkTxCd`) is a ready-made event-type taxonomy with three levels: domain, family and sub-family.”

   **What is wrong:** The three-level statement describes only the standard `Domain` branch. `BkTxCd` also supports a proprietary code and issuer, so an implementation cannot assume that every reported transaction has all three ISO taxonomy levels. Calling it an event type also overstates it: it classifies the bank transaction represented by an entry or transaction detail and is not an event identity or lifecycle-state model.

   **Correction:** Model both the standard domain/family/sub-family branch and the proprietary-code branch permitted by the applicable message version and usage rules; preserve the raw code and issuer, and treat the classification as an attribute whose granularity may be entry-level or transaction-detail-level.

   **Confidence:** High.

3. **Quoted sentence:** “The reversal indicator (`RvslInd`) flags an entry as the reversal of a previously booked entry.”

   **What is wrong:** `RvslInd = true` says that the reported entry is the result of a reversal. It does not identify the original entry, prove that the original can be found in the same message or dataset, or by itself establish the asserted “previously booked entry” relationship. An absent optional indicator is also not evidence of `false`.

   **Correction:** Store it as an optional reversal-result flag. Establish any link to an original entry from reversal/original-reference information or other reconciliation evidence; do not infer that link from `RvslInd` alone.

   **Confidence:** High.

4. **Quoted sentence:** “pain (customer to bank) and pacs (interbank) messages cover the payment lifecycle before booking.”

   **What is wrong:** This compresses message-family scope into directions and a booking boundary that ISO 20022 does not define. `pain` is the payments-initiation family and includes bank-to-customer status reporting as well as customer initiation. `pacs` is the payments-clearing-and-settlement family for FI-to-FI processing and includes status, return and reversal-related messages; those are not uniformly “before booking.” Account booking/reporting is represented principally by `camt`, but booking can occur at different participants at different points in the payment lifecycle.

   **Correction:** Describe `pain` as initiation and related customer-payment status/cancellation messages, `pacs` as FI-to-FI clearing, settlement, status, return and reversal messages, and `camt.052/.053/.054` as account reporting/notification. Model lifecycle stage and each party’s booking separately rather than assigning the families to a single pre-booking phase.

   **Confidence:** High.

5. **Quoted sentence:** “Model payments and postings as **non-historised (transactional) links**, or as a hub on the transaction ID with an insert-only satellite.”

   **What is wrong:** Payments and postings are different grains, and the two alternatives are not interchangeable. One payment can produce several account postings, fees, settlement legs and reversals. A non-historised link cannot by itself represent corrections to a payment–posting association; inserting a corrected link leaves both the erroneous and corrected associations apparently active. A hub is safe only when its business key is stable and collision-free in the chosen scope; a source-local transaction ID commonly is not.

   **Correction:** Give payment instructions, payment/settlement events and account postings explicit grains and durable scoped business keys. Represent their associations with links; where an association can be asserted, corrected or invalidated, historise/effectivity-date its status. Put changing descriptive observations in historised satellites while retaining the immutable raw versions and record source.

   **Confidence:** High.

6. **Quoted sentence:** “Events are immutable. Corrections arrive as new events, the way ISO 20022 handles reversals, never as updates.”

   **What is wrong:** An economic reversal is a new compensating event, but not every correction is a reversal or a new business event. A bank can later correct remittance text, transaction classification, counterparty data, references, status or even a previously supplied booking/value date for the same posting. Treating each corrected observation as a new event duplicates the economic occurrence; overwriting it loses audit history. ISO 20022 messages transport reports and amendments but do not impose universal event-sourcing semantics on the receiver.

   **Correction:** Keep the economic event identity immutable, model genuine reversals/returns as separate related events, and historise corrected observations about the same event as new satellite/assertion versions with source/system time. Never overwrite Raw Vault history, but do not manufacture a second economic event merely because an observation changed.

   **Confidence:** High.

7. **Quoted sentence:** “valid time = booking or value date”

   **What is wrong:** Booking date and value date are not alternative labels for one valid-time axis. Booking date is when an entry is posted to an account (and may first be pending); value date is when it takes effect for interest/value purposes. They can differ. Choosing one globally makes queries wrong: a back-valued posting loaded on 10 January with value date 8 January would appear to have existed on 8 January in an as-booked ledger reconstruction, while using booking date would make an interest calculation effective two days late.

   **Correction:** Define valid time per predicate. Preserve at least booking/posting effective time, value date/time, settlement time and lifecycle-status effective intervals separately where supplied. Use booking time for an as-posted ledger question and value time for value/interest questions; do not collapse them into a generic `valid_time` without a declared semantic role.

   **Confidence:** High.

8. **Quoted sentence:** “transaction time = load timestamp”

   **What is wrong:** A warehouse load timestamp records when this vault observed a row; it need not record when the source created, changed or knew the fact. Delayed batches, replays and migration loads can therefore make source history appear to begin days or years late. Calling the field transaction time without qualifying the observing system makes bitemporal ‘as known then’ claims ambiguous.

   **Correction:** Treat load timestamp as warehouse system/observation time and retain source creation/change/report timestamps separately. If the temporal claim is “what this warehouse knew,” load time may bound transaction time; if it is “what the bank/source knew,” source-recorded time is required, with ingestion time retained for lineage.

   **Confidence:** High.

9. **Quoted sentence:** “With this, the bitemporal model needs no update logic for events at all.”

   **What is wrong:** Physical immutability does not remove temporal versioning logic. Late-arriving corrections and retractions still require a new assertion version and either closure of the previous system-time interval or a deterministic rule that derives intervals/currentness. Otherwise two contradictory versions remain simultaneously current. For example, a posting reported on Monday with value date Friday and corrected on Tuesday to Thursday cannot support an as-known-on-Monday versus as-known-on-Wednesday query without version-ordering and interval semantics.

   **Correction:** Use insert-only storage if desired, but implement version succession, deduplication, retraction and interval derivation explicitly. Separate immutable event occurrences from mutable assertions about them and define how valid-time and system-time intervals are opened and closed or derived.

   **Confidence:** High.

10. **Quoted sentence:** “Keep three dates where available: value date, booking date and settlement/transfer date. In-transit measurement needs all three.”

   **What is wrong:** Settlement date and transfer/execution date are not one interchangeable date, and three dates are not sufficient for every in-transit measure. A payment can have initiation/acceptance, requested execution, interbank settlement, beneficiary-account booking and value dates, with several settlement legs. Conflating execution with settlement can produce a zero or negative transit interval or attribute intermediary delay to the wrong stage.

   **Correction:** Preserve separately every supplied lifecycle timestamp and its role, including initiation/acceptance, execution, clearing/settlement per leg, account booking and value time. Define each in-transit metric by named start and end events rather than by an assumed universal trio.

   **Confidence:** Medium.

## Unverified items

**Quoted claim:** “Their transaction resources are pragmatic, public and close to how core banking systems actually expose transactions **(unverified in detail)**.”

**Best answer:** The Berlin Group NextGenPSD2 and UK Open Banking specifications do publish consent-controlled account/transaction endpoints and pragmatic resource representations for booked and, where supported, pending transactions. The UK model exposes normalised account transaction resources; Berlin Group exposes account transaction lists/reports with booking-status and date filters, optional fields, and implementation-dependent extensions. The claim that these are “close to how core banking systems actually expose transactions” is not generally justified: they are regulated external API contracts and normalisation layers, commonly implemented through API gateways, consent/security layers and translation over one or more ledger/core systems. Their resources are useful source-interface patterns, but should not be treated as evidence of core-bank physical or canonical models.

**Confidence:** High for the public, consent-controlled transaction-resource characterisation; Medium for implementation proximity because it varies by bank and platform.

verdict - FAILS + a correction to an existing posting’s value date is a new version of the same observation, not an economic reversal or a new immutable event

## Pass 2 — sol's answer, verbatim

## Findings

1. **Quoted sentence:** “It classifies a transaction; it is not an event identity or lifecycle state.”

   **What remains wrong:** Finding 2 was applied only partially. `BkTxCd` can classify the bank transaction represented at `Ntry` grain or at `TxDtls` grain; the revision omits that distinction and reduces both to “a transaction.” The failure case is an aggregated entry with several transaction details: an entry-level code describes the aggregate bank entry and cannot safely be copied to every underlying transaction as though each detail supplied that classification.

   **Correction:** State that `BkTxCd` may occur at entry or transaction-detail level and retain the level at which each code was reported. Do not promote an entry-level classification to transaction-detail grain without separate evidence.

2. **Quoted sentence:** “pacs covers bank-to-bank clearing, settlement, status, returns and reversals.”

   **What remains wrong:** Finding 4 specified FI-to-FI scope, but the revision substitutes the narrower “bank-to-bank.” ISO 20022 `pacs` messages are financial-institution-to-financial-institution messages; the participants need not both be banks. The failure case is a `pacs.008` exchanged through a clearing or settlement institution, or involving a qualifying non-bank financial institution: classifying the family as bank-to-bank excludes an in-scope message flow.

   **Correction:** Replace “bank-to-bank” with “financial-institution-to-financial-institution (FI-to-FI).”

verdict - FAILS + an entry-level BkTxCd on an aggregated entry cannot safely be treated as the classification of each underlying transaction detail
