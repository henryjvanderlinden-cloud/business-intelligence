Astra's answer, verbatim (relative links re-based from scratch/ to this folder):

1. **Concurrency.** Two agents start from the example's eight evidence files and both read the table folder before writing. Agent A analyses item 15 and creates `E009_profile.json`; agent B analyses item 17 and independently creates `E009_profile.json`. Both runs are new, neither agent edits an existing evidence file, and each changes only its own item document and supporting evidence. Their branches produce an add/add conflict. The README supplies neither an allocation rule for evidence IDs nor a reservation mechanism. If they instead choose `E009_quality.json` and `E009_volume.json`, git can merge cleanly, but both item files contain `evidence: [E009]`, which now resolves to two files in the same evidence directory. This is a silent inconsistency under the stated naming rules.

   There is also a collision built into column ownership. An agent analysing item 02 and another analysing item 03 of `BackorderOrderID` must both update `columns/BackorderOrderID.md`, including its shared `finding`, `evidence` and analysis metadata. Item ownership does not imply file ownership when a column file holds several items. The sentence "Two agents working on different items of the same table ... never touch the same file" is therefore false even before evidence allocation is considered. Treating "one writer" as an externally guaranteed exclusive assignment would prevent this second scenario, but would require coordinating ownership at column-file granularity rather than relying on the stated item partition.

2. **Predictability.** A plausible ERP column named `[Unit/Price]` in SQL Server would require `columns/Unit/Price.md`: the slash becomes a path separator instead of part of the filename. `[AUX]`, used as an auxiliary flag, would require `AUX.md`, a reserved Windows device name even with the extension. A column named `[Klantnaam beëindigd]` cannot simultaneously preserve its source spelling and satisfy the ASCII-only naming rule. These are hypothetical ERP identifiers, not claims about WWI's actual schema. The relevant platform rules are documented in Microsoft's [database identifiers](https://learn.microsoft.com/en-us/sql/relational-databases/databases/database-identifiers) and [Windows file naming conventions](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

   Independently of Windows restrictions, concatenation is not injective: schema `Sales.EU`, table `Orders`, and schema `Sales`, table `EU.Orders` both map to `Sales.EU.Orders`. Delimited identifiers permit these names. Preserving case does not solve either collision or illegal characters; a reversible escaping rule is missing.

3. **Searchability.** A plausible question is: "The evidence for this key changed; which findings, including findings on other tables that depend on it indirectly, need rechecking?" A grep for its evidence ID finds direct textual mentions, with false matches in other tables because evidence IDs are local. A grep for its file path can find direct incoming links. Neither supplies the transitive dependency closure, and a link is not required to identify the particular assertion being relied on. Arbitrarily long chains of cross-table dependencies are permitted. Answering the question needs traversal and interpretation, or a derived dependency index with a more precise dependency representation; one or two glob/grep commands can retrieve candidate text but cannot determine that answer.

   Even the advertised simple topic query is incomplete: `analysis/wwi/tables/*/19_sensitivity.md` does not find sensitivity recorded only in a column's item-19 section, which the column-file rule permits. Searching column bodies as well can repair candidate retrieval, so this is a defect in the advertised query, not proof that all topic searches require an index. Likewise, the presence of a column file establishes that *some* topic was analysed, not which remaining column topics are complete.

4. **Example compliance.** The following deviations are present in [the example](../../../analysis/wwi/tables/Sales.Orders/) relative to [the README](../../../analysis/README.md).

   - **The column front matter is not the promised same front matter with `item: column`.** `columns/BackorderOrderID.md` omits `topic` and `tier`. Its topic confidences are embedded in headings such as `## 02 Meaning — confidence: high`, rather than given their own `confidence` lines. The README also leaves unresolved what one `tier` should mean for a column containing both minimum and best-effort items; omission does not implement the stated format.
   - **Authored text is not ASCII.** `03_temporal.md` contains em dashes and a section sign; `06_keys.md`, `07_population.md`, `19_sensitivity.md` and `columns/BackorderOrderID.md` contain em dashes. These are authored punctuation, not non-ASCII values quoted from the source, so the stated exception does not apply.
   - **Findings are repeated rather than owned once.** `01_granularity.md` and `06_keys.md` both assert and evidence `OrderID`'s declared and observed uniqueness. The direction of `BackorderOrderID` is asserted in `01_granularity.md`, `06_keys.md` and the column file. The latter two table files do link to the column file, but still restate the conclusion as maintained text; they are not generated views. This departs from "Each finding lives in exactly one file" and creates the drift the README says it avoids.
   - **Facts about other tables have no links to those tables' analysis files.** For example, `01_granularity.md` gives the number of `Sales.OrderLines` per order; `07_population.md` gives customer and contact facts; `19_sensitivity.md` relies on `Application.People`. Evidence E008 supports measurements, but an evidence reference is not the cross-table file link required by working rule 2. Missing destination analyses explain the absence, but the rule gives no exception for them.
   - **E001–E004 lack the required manifest hash.** Their `as_of` records identify a live database and a calendar date, not a pinned source snapshot with a manifest hash. An extract hash should not simply be added as though it identified the live catalogue query; these are different evidence sources.
   - **E005–E008 do not hold the computation.** Each records `tool: prototypes/information_analysis/evidence_orders.py`, but no query or code content. That locates a mutable script rather than retaining the computation within each evidence record as promised. All eight files record `written_at`; none separately identifies when the underlying query or computation ran. In particular, the catalogue results were imported from earlier requests, so their common write timestamp is not evidence of the query execution time.
   - **The literal aggregates-only rule is not followed.** E001–E003 retain individual catalogue rows for columns and constraints, and E004 includes a table-description value. These are metadata, not extracted customer-order rows, but they are also not aggregate results. The README needs a metadata exception if that is intended; it currently says "Results are aggregates" without one.
   - **The implemented claims have no retained implementation evidence.** `03_temporal.md` and the column file describe Microsoft simulator procedures based on a "summarising fetch". None of their listed evidence files contains that fetched code, its version, or the retained fetch result. Their `claims` include `implemented`, but the evidence set contains only catalogue queries and extract profiles.
   - **Unresolved minimum findings do not consistently receive `confidence: unknown`, and some are guessed.** `06_keys.md` says "Key stability: probably stable, not proven" under an overall `confidence: high`; "probably stable" is precisely a guess about an unestablished part of a minimum item. `03_temporal.md` records an unknown time zone under `medium`, `07_population.md` records unknown cancellations and backlog meaning under `medium`, and `19_sensitivity.md` records unknown legal basis and retention under `medium`. Stating these uncertainties in prose does not follow working rule 3's instruction to write `confidence: unknown`. The sensitivity file additionally includes a low-confidence impression that customer names denote natural persons, without measured support. A single confidence field cannot express the mixture cleanly, but the example does not resolve that mismatch.

   The evidence files alone cannot establish whether they have previously been edited, so no historical immutability breach is inferred. However, their named generator's `write` function opens the fixed E001–E008 paths with mode `w`; rerunning it would overwrite them instead of creating the new files required by the README. That is a prospective violation in the example's evidence-production path, not a claim that a rerun occurred. No missing best-effort item or missing unanalysed column is counted as a deviation: the README explicitly permits absent files.

5. **Column files and topic folders.** The categorical file-per-column choice fails for a plausible ERP `CustomFields` column containing hundreds of tenant-specific JSON properties. Item 11 would describe nested types and formats, item 02 would define business meanings per tenant, item 10 would hold their code domains, and item 19 would classify individual nested values. Independent agents could own those subjects, and individual findings could change without the others. One column file would cease to be small and would become a shared write target. WWI's `Warehouse.StockItems.CustomFields`, identified in [129](../../10_architecture/129_information-analysis.md), supplies a real example of the *kind* of column; hundreds of tenant-specific properties are the counterexample scenario, not an observed claim about WWI. This disproves the premise that a column's findings necessarily "belong together and are short"; it does not require a folder for every ordinary scalar column.

   The four cross-table exceptions are also not exhaustive. A reconciliation assertion that postings in several journal tables agree with an external ledger control total belongs to item 16, not inherently to relations, processes, terms or entities. Filing copies under every table violates single ownership; selecting one table as the canonical home is possible, but no selection or discovery rule is specified, and the finding does not belong to that table alone. A source-wide reconciliation could use `_source` if that directory is interpreted broadly; one spanning two ERP sources and an external control report still has no prescribed landscape-level home. This calls for a canonical place for set-level assertions, not necessarily a second topic tree duplicating all findings.

6. **Compatibility with 120 and ADR-0011.** There are substantive mismatches if this layout is the record of the analysis, as proposed, rather than a temporary view of a separate assertion store.

   [ADR-0011](../../20_decisions/0011-assertions-identity-plane-publication-gate.md) says: "Every claim the system holds is a typed assertion with its own attributes: subject, claim type, lifecycle status, authority, evidence bundle, scope, volatility, owner, retention class and privacy class." It also says: "A card is a bounded, readable projection of the assertions about one stable business object" and "It is not where knowledge is kept." The README instead supplies one shared record with `claims: [declared, observed]`, one status and one evidence list for an item containing several claims, and bundles still more claims into each column file. There is no separately represented assertion to which those attributes attach. For example, the declared backorder direction and the opposed observed direction share `status: proposed` and `confidence: high`; either cannot be contested or retracted independently in the proposed record format. Free prose preserving both statements is insufficient to supply their individual lifecycle and authority.

   [120](../../10_architecture/120_context-layer.md) specifies "lifecycle status — proposed, accepted, contested, superseded or retracted". The README instead permits `proposed | ruled | stale`. Staleness describes evidence freshness and can coexist with an accepted or contested claim; making it an alternative to `ruled` discards that distinction. The format offers no representation of the other assertion lifecycle states or a mapping to them.

   ADR-0011 says claim types carry "each with its own effective time and observation time." A shared `as_of` and `analysed_at` do not supply those two times per claim, particularly when live catalogue declarations, historical extract measurements and fetched implementation descriptions are combined in one item. The same ADR says: "All stores share one scheme of permanent identifiers." The README's literal source-name paths and `subject: wwi/Sales.Orders` provide neither a permanent identity independent of a rename nor an alias mechanism. This conflicts with 120's explicit requirement: "Every object has a permanent identifier that does not change when the object is renamed, moved or re-platformed."

   For evidence, 120 says: "It is content-addressed and holds" the computation, parameters, "the tool and code version", privacy classification and an assertion-specific "invalidation predicate". It then specifies: "Staleness is decided by that predicate, not by the mere fact that some evidence changed." The README's sequential evidence IDs are not content addresses; the source manifest hash identifies input, not the evidence bundle. No per-assertion invalidation predicate is recorded. Working rule 5 substitutes a generic newer-extract-disagrees rule, which cannot express, for example, an assertion requiring rechecking when a previously excluded tenant first appears even though the old observed population still agrees.

   The confidence scale also says **high** may mean "ruled by a person". But 120 explicitly says decisions have "the highest authority, which is not the same as the highest truth" and that "A person with authority can define net revenue correctly and still be wrong about how the warehouse actually computes it." Applied to a mixed item record, a ruling alone can therefore raise descriptive confidence without supporting observation. Confidence in a ruling's provenance can be high; that is not the same as high confidence in every bundled factual claim.

   No direct contradiction with ADR-0011's publication gate is established. This layout does not instruct publishing untested artifacts, and ADR-0017 explicitly preserves the gate while allowing incomplete analysis. Likewise, immutable aggregate evidence in git is not itself a contradiction: 120 requires retained evidence snapshots, and ADR-0011 leaves the physical assertion medium open. The failures above concern assertion granularity, identity, lifecycle and evidence semantics, not the mere use of folders and Markdown.

VERDICT: FAILS + two compliant item writers can allocate the same local evidence ID, producing an add/add conflict or silently ambiguous evidence references.
