## sol's answer, verbatim

1. **The audit satellite can silently discard a newly delivered zero-length version when the current and history extracts are not one atomic snapshot.**

   > `row_number() over (partition by typed."CustomerID", source_ts order by source_end nulls last, row_hash) as source_seq`
   >
   > `where t.hk_customer = i.hk_customer and t.record_source = i.record_source`
   > `  and t.source_ts is not distinct from i.source_ts and t.source_seq = i.source_seq`

   The positional discriminator is stable only if every member of a same-key, same-start-time group is present the first time any member is loaded. The group-expansion query does not provide that guarantee across separately copied current and history tables. Suppose transaction 10 updates customer 1 twice, producing zero-length history row `(1, 'A', ValidFrom=10, ValidTo=10)` and current row `(1, 'B', ValidFrom=10, ValidTo=9999)`. If day 1 copies history before the commit and current after it, staging sees only `B` and stores it as `(source_ts=10, source_seq=1)`. Day 2's full extracts contain both rows; staging assigns `A` sequence 1 and `B` sequence 2. The audit `not exists` mistakes `A` for the previously stored `B`, suppresses `A`, and inserts a second copy of `B` at sequence 2. A vault rebuilt from the whole day-2 history contains `A/1, B/2`; the incremental vault contains `B/1, B/2`. This source history obeys the stated SQL Server behavior; the missing requirement is a transactionally consistent joint extract, or a non-positional immutable version identity.

2. **The claimed full-reread detection of rewritten history is not implemented by the supplied audit SQL.**

   > “an edit made with versioning off is seen only by the full reread of §4 item 4, where the rewritten-version test fails loudly.”
   >
   > `and t.source_ts is not distinct from i.source_ts and t.source_seq = i.source_seq`

   The collision check ignores `row_hash`, so a full reread cannot put a rewritten version into the audit satellite; the only supplied test compares delivery with staging, not staging with the already stored audit identity. For example, first load history row `(CustomerID=1, CustomerName='A', ValidFrom=10, ValidTo=20)`, giving identity `(10,1)`. With versioning off, change that row to `CustomerName='B'`, then run Sunday's full reread. Staging contains `B` and the nothing-dropped test passes, but the audit model finds the old `(10,1)` and inserts nothing. The vault retains `A`. The note promises a loud failure outside the append-only assumption, but none of the generated SQL shown performs the required old-hash/new-hash comparison.

3. **The “nothing dropped” test proves only a row count, not that every delivered row arrived exactly once.**

   > `select ... as expected, (select count(*) from {{ ref('stg_wwi__sales__customers') }}) as staged`
   > `where ... <> (select count(*) from {{ ref('stg_wwi__sales__customers') }})`

   No key, hash, multiplicity, or sequence from `k` is compared with staging. With delivered rows `A=(1,'A',10,10)` and `B=(1,'B',10,9999)`, any staging defect yielding `B` twice and no `A` still has expected count 2 and staged count 2, so the test returns no failure. The concrete sequence-collision case above produces exactly the corresponding wrong audit outcome—two `B` versions and no `A`—while this test remains green. A count equality cannot support the note's claim “did every row delivered ... arrive, exactly once?”

4. **The periodic reread does not bound detection when an out-of-overlap row disappears before the reread.**

   > “at a fixed interval the whole set is read anyway ... The interval bounds how long a miss can stay unseen.”
   >
   > “with versioning switched off ... a retention policy deletes old history on its own”

   That bound holds only while missed rows remain in the source until the next successful full reread, a condition the note does not state. Let the stored maximum start time be 100 and the overlap produce bound 99. A long transaction begun at 98 commits on Saturday and delivers history row `(CustomerID=1, 'A', ValidFrom=50, ValidTo=98)`. Saturday's `ValidTo > 99` filter misses it. If retention removes that row before Sunday's full extract, the full reread and its count test both pass and the miss is never detected. Thus the proposed backstop does not meet the requirement to say when and how violations of the timing/append-only assumptions are detected.

5. **Two complete extracts cannot establish the proposed behavioral classes, and incremental observation cannot detect the counterexample claimed to change the class.**

   > “The information-analysis phase can put every source table in one of these classes, from evidence alone”
   >
   > “The measures, from two or more consecutive complete extracts”
   >
   > “The measures are cheap enough to recompute on every load and compare with the recorded class.”

   Two snapshots show what happened during one interval, not that rows “never change once written or closed.” For example, extracts on days 1 and 2 contain unchanged row `(id=1, value='A', created_at=1)` plus new rows, so the table is labelled accumulating and loaded with a `created_at` watermark. On day 3 the source corrects row 1 to `value='B'` without changing `created_at`, and adds `(id=3, created_at=3)`. The incremental read sees only row 3 and leaves `A` in the warehouse. Recomputing the advertised changed-row measure would require rereading and comparing old row 1—the total-history work the rule claims to avoid. The evidence supports a provisional hypothesis plus monitoring or a source guarantee, not the asserted classification and watermark rule.

VERDICT: FAILS [the positional version identity can silently suppress a newly delivered zero-length version]
