## sol's answer, verbatim

**A key represented only by history in the first full extract is classified as present, so the mart can create sales facts for invoice lines that were already absent when the warehouse first saw them.**

> “A key is present unless the latest row of its status-tracking satellite says `absent-unresolved`.”
>
> `where not _is_history and hk_invoice_line is not null`

On the first load dated 2016-06-02, let invoice line 900 have a historical source row `(source_ts=2016-05-01, ExtendedPrice=120, TaxAmount=20, _is_history=true)` but no current row because it was deleted on 2016-05-20. The hub, payload satellite and link loaders consume that historical row, but `present` excludes it and `latest` is empty, so the status loader emits no row for 900. Section 3 therefore defaults 900 to present; its PIT, bridge, computed satellite and fact can emit a £100 sale even though the complete extract says the line is absent. The grain and object-key tests agree with the same erroneous “present” rule, so they do not expose the ghost line.

**`load_date` is a manifest date rather than the time of warehouse acquisition, so a late-delivered extract rewrites earlier knowledge and makes the promised knowledge-time answer false.**

> “Knowledge time is the delivery's date, not the runner's clock.”
>
> “what the warehouse knew on any earlier date can be computed again from the rows with `load_date` up to that date.”

Suppose the 2016-06-03 extract is loaded on June 3, while a delayed extract whose manifest says 2016-06-02 is first received and loaded on June 4 and contains customer 42 with segment `Retail`. Its rows are stamped `load_date=2016-06-02`; after June 4, `__as_known(DATE '2016-06-02')` includes customer 42 even though the warehouse knew nothing about it on June 2. Insert-only storage cannot recover the actual acquisition order because the only wall-clock evidence is outside the rows queried by the macro. This is an unstated limit of the one-parameter reconstruction, not a declaration/template publication limit.

**A bridge can walk through an absent intermediate hub using its stale effectivity row, yielding either a false customer assignment or a dropped fact depending on how the mart joins the intermediate PIT.**

> “each step through the current link of rule 3”
>
> “a step with no current link leaves that key empty.”

On 2016-06-01, line `L1` links to invoice `I1`, and `I1` links to customer `C1`; on 2016-06-02, `I1` is `absent-unresolved` while `L1` remains present, and no new effectivity row ends `I1 -> C1`. Rule 3 still calls the last effectivity row current, so `brg_invoice_line__sale` walks `L1 -> I1 -> C1` through a hub that rule 4 says must be left out. If the fact trusts the bridge, `L1` is assigned to `C1` without a present invoice; if it inner-joins `pit_invoice` for the invoice date, `L1` disappears. The proposed bridge test checks only that the bridge has key `L1`, not that every traversed hub was present or that the reached keys were correct.

**The tests can all accept a fact whose lines have been assigned to the wrong customers and whose amounts have been exchanged between lines, because they test cardinality and grand totals rather than lineage.**

> “The fact table's key is unique, and it has exactly as many rows as there are invoice lines known and present.”
>
> “The sum of each measure equals the sum of the same column over the current rows the source delivered in this load.”

Let staging contain `L1 -> C1` with sales 100 and profit 20, and `L2 -> C2` with sales 200 and profit 50. A defective bridge/fact join that emits unique rows `L1 -> C2` with 200/50 and `L2 -> C1` with 100/20 has two rows, preserves every hub-object key set, reconciles to sales 300 and profit 70, finds exactly one valid dimension row for each lookup, satisfies the per-row arithmetic oracle if all line payload columns move together, and is reproduced by replay. Yet every segment receives the other segment's sale. Comparing totals with staging is independent only of the vault's aggregate calculation, not independent evidence that each delivered line followed the correct PIT, link, bridge and dimension path.

**The general “last in source order” rule is not a total order once more than one record source contributes a key, so the same raw rows can produce different current values.**

> “`record_source`, `source_ts` and `source_seq` together are the source version”
>
> “A satellite's current row for a key is the last of its rows in source order (`source_ts`, `source_seq`).”

For key `C7` on 2016-06-02, let source `CRM` deliver `(source_ts=2016-06-01 10:00, source_seq=1, segment='Retail')` and source `ERP` deliver `(source_ts=2016-06-01 10:00, source_seq=1, segment='Wholesale')`. Both source versions are distinct by the raw-vault key, but section 3 orders them identically because it omits `record_source` and declares no source precedence or survivorship rule. A PIT can therefore point to either value depending on physical/window tie order. One clean WWI source cannot justify the claimed general rule, and a table macro cannot turn this partial order into exactly one reproducible state.

VERDICT: FAILS initial-history keys default to present
