## sol's answer, verbatim

1. **FAILS — hidden output is not confined at the job boundary.** `Invoke-Holdout` returns arbitrary last-line JSON, `Get-HoldoutCode` returns arbitrary text, and the action handlers publish those values. A child emitting `{"status":"error","code":"IO","message":"private diagnostic"}` causes an export response's `generation` to contain that diagnostic. A child emitting `{"status":"error","code":"private diagnostic"}` puts it in both the response and `job.log`. These are counterexamples to containment if a child violates its reported output contract, not claims that the unseen scripts do so. Process/read exceptions also escape to the main catch, which publishes their messages. Ordinary stderr is drained without being published; that alone does not establish section 4's boundary. Minimal fix: catch process/stream failures inside the wrapper, map them to fixed codes, allowlist reported error codes, validate each success schema recursively, and construct public responses from approved fields rather than forwarding the child object. Unknown shapes must become a fixed protocol error.

2. **FAILS — the process timeout is not an end-to-end deadline.** In `Invoke-Holdout`, a process can exit while a descendant retains its stdout handle. `WaitForExit` then succeeds, `outTask.Wait(10000)` returns false, and the unconditional `outTask.Result` blocks until that handle closes, potentially indefinitely. On the timeout branch, .NET Framework's parameterless `Kill()` kills only the immediate process; exceptions are swallowed, termination is not awaited, and the wrapper returns while a surviving process could still write files. Concurrent `ReadToEndAsync` calls are supported on this runtime and avoid the ordinary full-pipe deadlock, but do not fix these cases. Minimal fix: enforce one deadline across process exit and both drains, never read `Result` after an unsuccessful wait, contain the process tree with a Windows Job Object, and terminate/reap it and dispose streams/process handles in cleanup. Treat failure to establish termination as an operational failure, not as completed cleanup.

3. **FAILS — setup neither proves the scheduled identity can write nor guarantees disabled installation.** The writable probe runs in setup's context, while the scheduled principal is `S4U, Limited`. A hidden directory writable only by Administrators passes an elevated setup probe but rejects the limited job's writes. If `code` is absent, setup skips the probe and still enables the job, contrary to section 4. Registration creates an enabled task before the subsequent disable call: a trigger between those calls can start it before Python exists; disabling a task does not stop an already running instance. An existing task can also run while its pin directory is being replaced. Minimal fix: disable and stop an existing instance before replacing pins, register the replacement disabled, require the reported command files and `common.py` to be installed, and verify Python execution and hidden-folder create/delete access under the actual scheduled principal before enabling. Copying the scripts directly between the two external folders does keep their contents out of the repository; the new block's failure is its installation/enablement protocol.

4. **FAILS — CRM retention depends on successful progress through generation.** `Do-Export` deletes old WWI dates before invoking `Do-Generate`; CRM deletion happens only after `Invoke-Holdout` returns. With four paired dates, a generator that takes 30 minutes leaves the oldest CRM extract present for those 30 minutes after its WWI partner was deleted. If `Process.Start` throws, `Do-Export` catches it as `code='job'`, but cleanup is skipped altogether and the orphan remains. Minimal fix: delete the corresponding CRM date as part of WWI retention, independently of generation, and reconcile orphans on subsequent runs even after failures. The added generation call follows WWI publication and marker clearance, so an ordinary reported generation error preserves those commits. The old export free-space check remains, and the generator report supplies both generation-volume checks; those checks do not cure skipped retention. The supplied main loop processes every pending request, so “one request per run” already fails with two queued requests, but that loop behavior predates this diff and is not a regression caused by the change.

5. **FAILS — invocation and result handling do not implement the complete reported contract.** The option names, optional duplicate files and literal `none` match the reports, but these concrete boundary cases fail:

   - `--repo` with the valid Windows directory `C:\work space\repo\` becomes `"C:\work space\repo\"`. Windows argument decoding treats the final backslash as escaping the closing quote, corrupting that argument and potentially consuming the next one. Spaces alone work. Replacing quotes with `\"` also fails to double existing backslashes before embedded quotes; a literal quote is not a valid Windows filename character, but this is still not a correct general argument encoder. Use the Windows CRT quoting algorithm, including doubling trailing backslashes before the closing quote.
   - The reports accept `E[1-9][0-9]*`; the job rejects `E1000` and admits `E0` and `E01` to the child. Match the reported expression in both actions.
   - Valid JSON is accepted regardless of exit code: `{"status":"ok"}` followed by exit 1 is returned as success. `Do-Score` also accepts `{"unexpected":1}` or JSON `null` because it rejects only status `error`. Require exit 0 plus the action's complete success schema, or exit 1 plus the documented error shape; reject every other combination. Last-nonblank-line parsing works for the reported single-line output, but does not validate that contract.
   - Under Windows PowerShell 5.1 StrictMode 2, `$r.PSObject.Properties.Name` throws for the empty object produced by `{}`. This was reproduced on Windows PowerShell 5.1.19041.6456 using an in-memory probe. A nonempty object lacking `status` returns false, so testing only that case misses the defect. Use `$r.PSObject.Properties['status']` and `['code']` after checking the object type, then validate their values. Missing required request fields likewise need explicit checks before property access.

VERDICT: FAILS [output containment, process termination, setup enablement, retention and interface validation have concrete counterexamples].
