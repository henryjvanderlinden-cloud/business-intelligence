## 1. What this note does

It says what the generator of ADR-0032 writes, from what, and how each generated model loads, so that the raw vault
of Wide World Importers declared in `model/` can be built and loaded in DuckDB by the runner of
[ADR-0015](../20_decisions/0015-sandbox-warehouse-dbt-duckdb.md). It covers, in order: the files (§2), the hash keys
(§3), the metadata every row carries (§4), the load pattern of each kind (§5), ordering, ties and late arrivals (§6),
the first day (§7), batches (§8), the meeting with staging and landing (§9), the tests (§10), and what is not
decided (§12). Three choices are put to the author (§11).

Facts this note rests on, checked on 2026-11-03:

1. The runner lands each complete extract as text into `landing.<schema>__<table>`, replacing the previous day's, with
   a column `_nsdn_load_date`, then runs `dbt build` on `prototypes/wwi_sandbox/dbt/`; when that project changes and
   no new extract waits, it rebuilds the latest date (`runner.py`). Any file written into the project goes live on
   the author's machine within a minute.
2. An extract holds 48 tables: the 31 base tables and the 17 history tables (`_Archive`), each complete
   (`manifest.json`, `"extract": "full"`). Three are kept (2016-05-31, 06-01, 06-02, 59 MB each).
3. Timestamps arrive with seven decimals (`2013-01-01T12:00:00.0000000`). DuckDB's `TIMESTAMP` keeps six and
   truncates the seventh; `TIMESTAMP_NS` keeps all seven (tested in DuckDB 1.5.6, the runner's version).
4. In the 17 system-versioned tables, **11 versions share their start time with the next version of the same key**
   (People 3, StateProvinces 7, Customers 1; query `s12-ties` on the sandbox). Every one is a zero-length version:
   `ValidFrom = ValidTo`. SQL Server writes these when a row is updated twice in one transaction.
5. Every WWI hub has one mapping and a one-part key; no composite key is declared yet. The generator still handles
   both (§3), because the format allows them.
6. The source types in use: `int`, `bigint`, `nvarchar`, `datetime2(7)`, `date`, `decimal`, `bit`, `geography`
   (delivered as WKT text) and `varbinary(max)` (delivered as `0x…` hex text).

## 2. The files

1. **The generator** is one Python file, `prototypes/vault_generator/generate.py`, standard library only, with its
   SQL templates beside it in `templates/` (one per kind, Python `string.Template`, so the templates' `$name`
   placeholders never clash with dbt's `{{ }}`). It reads `model/` through `tools/model_lib.py` and the source types
   through `model_lib.catalogue()`, the one reader of catalogue evidence. It is run by a person or the agent layer,
   never by the runner (ADR-0032 decision 6).
2. **What it writes**, into the dbt project, mirroring `model/`:

   ```
   prototypes/wwi_sandbox/dbt/models/
     staging/wwi/stg_wwi__<schema>__<table>.sql      one per base table used: typed, keyed, hashed (view)
     raw_vault/hubs/hub_<concept>.sql
     raw_vault/links/lnk_<from>__<role>.sql
     raw_vault/satellites/wwi/sat_<parent>__wwi[__<part>].sql
     raw_vault/satellites/wwi/sat_<hub>__wwi__audit.sql          by rule (149 Rule 3)
     raw_vault/satellites/wwi/sts_<hub>__wwi.sql                 by rule (149 Rule 7)
     raw_vault/satellites/wwi/eff_<from>__<role>__wwi.sql        by rule (149 Rule 6)
     raw_vault/reference/wwi/ref_<table>__wwi.sql
     <each folder>/_generated.yml                               columns, types, tests
   ```

   The effectivity satellite's name is the link's name without `lnk_`, plus the source, so it sorts beside its link.
3. **Every generated file starts with a header** (ADR-0032 decision 2):

   ```sql
   -- GENERATED by nsdn vault generator 0.1.0 from model/raw_vault/hubs/hub_sales_order.md
   --   declaration nsdn:rv:hub:sales_order, sha256 3f2a…(12)   template hub.sql, sha256 9c1e…(12)
   -- DO NOT EDIT. Change the declaration or the template and regenerate.
   ```

   No date or time goes in the header, so regenerating unchanged input gives an empty diff. The generator version is
   a constant in `generate.py`, raised with every change to its output and named in the release notes of ADR-0036.
4. **`generate.py --check`** regenerates in memory and fails if any generated file differs from what is on disk or
   carries no header, and if any file in the generated folders was not written by the generator. It will become part
   of `tools/check_repo.py`, which is how "never edited" is enforced rather than hoped for.
5. **Only declarations with `status: accepted` are generated.** A declaration of another status produces nothing,
   and a generated model whose declaration is gone is removed by the next run.
6. The hand-written smoke model `stg_wwi__orders.sql` is replaced by the generated `stg_wwi__sales__orders.sql`.

## 3. Hash keys

ADR-0030 left open the algorithm, the key preparation and the representation. Proposed:

1. **Algorithm: SHA-256**, written as 64 lower-case hexadecimal characters (`VARCHAR`). MD5 is the older Data Vault
   2.0 default and half the size, but a financial client's security review will flag it regardless of the
   (negligible) collision risk, and the cost here is a few hundred MB at most. DuckDB has `sha256()`; PostgreSQL has
   `sha256()` with `encode(…, 'hex')`, so the same keys come out at a PostgreSQL client.
2. **Hub key input**: the key-space code, then each key part in key order, joined by `|`:
   `wwi|832`. **Link key input**: the input of the `from` end, then of the `to` end, each with its own key space:
   `wwi|1|wwi|832`. The link's role is not part of the input: two links between the same hubs are different tables
   and never share a key column.
3. **Preparation of each part**, applied only to the hash input, never to the stored business key (144 §6 item 1):
   cast to text in a fixed form (integers without leading zeros or decimals; decimals with their declared scale;
   dates and timestamps in ISO 8601 with seven decimals); trim leading and trailing spaces; then escape `\` as `\\`
   and `|` as `\|`, so that no two different keys can produce the same input.
4. **Case**: a key that the source compares without regard to case must hash the same whatever case it arrives in.
   SQL Server compares case-insensitively by default; PostgreSQL does not. Proposed: a field `key_case` on the source
   declaration, `fold` (upper-case before hashing) or `exact`; WWI is `fold`. This adds a field to a ruled format
   (§11, choice 3). For WWI it changes nothing, since every key is an integer.
5. **An empty part means no key.** If any part is null or empty after trimming, the hash key is null and no hub or
   link row is written. The row's satellites are not affected (the optional relationship is kept as delivered,
   149 Rule 5). A mandatory key that arrives empty fails a test (§10).
6. **The business key is stored as delivered**, beside the hash key, in the hub, so a person or agent can always read
   which key a hash stands for (ADR-0030, Consequences).

## 4. What every row carries

Every generated raw-vault table carries these metadata columns, in this order, before its payload:

| Column | Meaning | Type |
|---|---|---|
| `hk_<object>` | the hash key (hubs, links; in satellites the parent's) | `VARCHAR` |
| `load_date` | **knowledge time**: the date of the extract that delivered the row (`_nsdn_load_date`) | `DATE` |
| `batch_id` | the batch: the extract's date and source, `wwi:2016-06-02` | `VARCHAR` |
| `record_source` | the source table, `wwi:Sales.Orders` | `VARCHAR` |
| `source_ts` | **source system time**: `ValidFrom`, or `LastEditedWhen`; empty where the table has neither | `TIMESTAMP_NS` |
| `source_seq` | the position among versions of one key with equal `source_ts` (§6); 1 almost always | `INTEGER` |
| `row_hash` | SHA-256 of the whole delivered row, every column as delivered, in catalogue order | `VARCHAR` |
| `valid_from` | **business valid time** from the declared column, or empty | as the column |
| `valid_from_basis` | `column`, `unknown` or `sampled`, from the declaration's `valid_time` | `VARCHAR` |
| `hashdiff` | SHA-256 of the columns change detection compares (§5) | `VARCHAR` |

1. `record_source`, `source_ts` and `source_seq` together are the **source version** of 149 Rule 2. With the parent
   key they are the key of every satellite row. Load time is not needed in the key: a source version is loaded once.
2. **Knowledge time is the delivery's date, not the runner's clock.** In the sandbox the extract is of a simulated
   day, so `load_date` is that day (2016-06-02), not the real day the runner ran (2026-10-20). Generally: knowledge
   time is the as-of date the delivery states in its manifest. This keeps a rebuild from the same extracts identical
   to the original load, which release regression needs (`ARC-OP-30`). The runner's wall-clock time stays in
   `nsdn_meta.load_log`.
3. Source system time is stored, labelled, and never offered as business time (ADR-0027 decision 2). `TIMESTAMP_NS`
   keeps all seven decimals; with six, versions a fraction of a microsecond apart would become false ties.
4. Payload columns get the types the catalogue states, mapped once in the generator: `int` → `INTEGER`, `bigint` →
   `BIGINT`, `nvarchar` → `VARCHAR`, `decimal(p,s)` → `DECIMAL(p,s)`, `date` → `DATE`, `datetime2(7)` →
   `TIMESTAMP_NS`, `bit` → `BOOLEAN`, `geography` → `VARCHAR` (the WKT text as delivered), `varbinary` → `VARCHAR`
   (the hex text as delivered). A type the map does not know stops the generator; it never guesses.
5. A column declared `load=never` (`HashedPassword`, ADR-0033) is generated as an always-empty column of its type.
   This is the one deliberate exception to exact reconstruction: what the source held is reconstructed for every
   column except those declared `load=never`, and the reconstruction test (§10) says so. Nothing derived from the
   value (no digest) is kept either, since that would still be a credential. A version that differs from the one
   before only in such a column is still recorded, as a row of the audit satellite (§5 item 6).
6. `row_hash` is computed once per delivered row, in staging, and is used only to number ties (§6 item 2) and to
   detect a rewritten version (§6 item 5); `HashedPassword` takes part in it in staging and is not stored.

## 5. The load pattern of each kind

Every raw-vault model is a dbt `incremental` model with the `append` strategy and `on_schema_change='fail'`: rows
are only ever inserted (ADR-0027, Consequences). Each pattern below is written out as full SQL in its file, with no
macro calls (ADR-0032 decision 2). "Incoming" means the rows of the staging view for this batch.

1. **Hub.** Insert each hash key from incoming that is not yet in the hub, once, with the business key as delivered,
   the earliest source version that brought it, and this batch's metadata.
2. **Link.** The same, on the link's hash key, with both ends' hash keys and, where declared, the columns kept
   (`kept=…`). One link table per mapping source table today; a second source adds a second select to the union.
3. **Payload satellite** (`satellite_kind: payload`). The `hashdiff` covers the declared columns, the business valid
   time included (127: a correction that moves only a date is kept). A source version is inserted if it is not yet
   in the satellite and its `hashdiff` differs from that of the version just before it in source-version order
   (§6), looking across both the rows already loaded and the incoming ones. So each satellite holds a row per source
   version in which its own columns changed (149 Rule 3). A late arrival adds one more rule (§6 item 6).
4. **Milestone satellite** (`satellite_kind: milestone`). As a payload satellite, except that the version before the
   first one is taken to be all empty. So the satellite starts at the first version where the milestone happened
   (`PickingCompletedWhen` filled), and a milestone later taken back (emptied) is recorded as a row of its own.
5. **Reading satellite** (`satellite_kind: reading`). Keyed by the parent and the reading's own key
   (`reading_key=yes`). A reading is inserted once, if its reading key is not yet there, and never superseded
   (149 Rule 10). No `hashdiff`.
6. **Audit satellite** (by rule). Holds `LastEditedBy` (where the table has it), source system time and the version's
   `row_hash`. It has **no
   change detection**: every source version not yet present is inserted, whatever its content, so every source
   version is exactly one row and the satellite is the source's version log (149 Rule 3). (149 Rule 3 describes this
   as change detection on both columns; that is not enough, because two versions in one instant by the same person
   have equal values for both.)
7. **Status-tracking satellite** (by rule, for hubs mapped from an `extract=full` table). Compares the keys of this
   complete extract with each key's latest status and inserts a row only on a change: `present` for a new key,
   `absent-unresolved` for a key missing from this extract, `reappeared` for a key that was absent and is back.
   `deletion-confirmed` is not generated now: the conditions of 127 ("Absence is not deletion") are not yet stated in
   a form a template can test, and are owed (§12).
8. **Effectivity satellite** (by rule, one per link). Per driving key, tracks which link row is current. *As built
   (§13 item 1): one row per change, carrying the hash key of the link current from that source version, or empty
   when there is none; "ended" is read from the next row.* The draft had two rows per change, the new link `active`
   and the previous one `ended`. The business start comes from the declaration's `effectivity_start`: a column (an event date or a
   milestone), `load` (the knowledge time), `presence in a complete extract`, or `unknown` (empty, labelled). For a
   bridge (`driving: none`, link 15), a link row is `active` while it is present in the complete extract and
   `absent-unresolved` when it is missing, as in the status-tracking satellite.
9. **Reference table.** Keyed by the code and the source version; inserted when the source version is new and its
   columns (with `LastEditedBy`, which stays in reference tables) differ from the version before (149 Rule 8).

## 6. Ordering, ties and late arrivals (owed under `ARC-OP-29`)

1. **The order of versions of one key** is by `source_ts`, then by `source_seq`.
2. **`source_seq` breaks ties, once per source row.** It is computed in the staging view of the source table, never
   per satellite, and every hub, link and satellite fed by that row carries the same number. Among the versions of
   one key with equal `source_ts`, they are numbered by their end time (`ValidTo`, earliest first, the current row's
   open end last), then by `row_hash` (§4 item 6), which covers every delivered column and is the same for every
   object. A zero-length version (start equals end) therefore always comes before the version that replaced it in
   the same instant. The numbering is stable from day to day: the zero-length versions sit in the history table,
   closed, from the start, and the version that follows them moves only its end time when it is closed later, which
   does not change its position. Tables that are not system-versioned hold one row per key per extract, so their
   `source_seq` is always 1. *Assumed, not proved:* the numbering stays stable only if no version is added later at
   an instant already loaded. SQL Server writes every version of one instant in one transaction and never adds to the
   history afterwards, so it holds for WWI; for a source where it does not, a late version at a loaded instant
   shifts the numbers after it, and the batch fails loudly on the rewritten-version test (§10 item 4) instead of
   loading wrongly (second review, finding 3).
3. **Whether to keep zero-length versions at all** is a choice for the author (§11, choice 1). The recommendation is
   to keep them.
4. **The same source version delivered again** (the current row of day 1 arrives in day 2's history table, or a
   boundary row twice on the first day) is loaded once. `ValidTo` is not part of the source version, so a version
   whose end has since been set is still recognised as the same.
5. **The same source version with different content** (equal source version, different `row_hash` from the one in
   the audit satellite, which keeps `row_hash`) would mean the source rewrote history without moving its clock. It
   is not loaded silently: a test fails the batch (§10), and the agent layer reports it.
6. **A late arrival** is a version whose `source_ts` is earlier than the latest version of that key already loaded.
   It is inserted, carrying its own (later) knowledge time, and compared with the version before it in source
   order. Inserting it can change what the version *after* it means: if that next version had no row in a
   satellite because it equalled its old predecessor, it would now wrongly inherit the late arrival's values. So
   each satellite also inserts a **restatement** of the next version: when a late version L is inserted, and the
   next source version N of that key (known from the audit satellite) has no row in this satellite, a row for N is
   inserted in the same batch, carrying the values that were in force at N before L arrived (those of the
   satellite row before L), unless they equal L's. Example: `t1 red` and `t3 red` loaded (only `t1` stored); late
   `t2 blue` arrives; the satellite inserts `t2 blue` and `t3 red`, and reconstruction at `t3` gives red, as the
   source held. Nothing already loaded is changed. A test reports late arrivals as a warning. "What did the source
   hold at time *t*" (by source version) then includes them; "what did we know on day *d*" (by `load_date`)
   correctly does not, before the day they came. In WWI none is expected: the history tables only ever add versions
   after the last one loaded, so this rule is built and tested on constructed cases.
7. **What a daily full extract cannot show.** For the 13 tables that are not system-versioned, two edits of one row
   between two extracts leave only the second (the first is lost to everyone); their history is sampled per day
   (127). The audit satellite makes this visible: a jump in `LastEditedWhen` with no row in between.

## 7. The first day

1. **One pattern for every day.** The staging view of a system-versioned table is its current rows and its history
   table together (a column `_is_history` says which). Because every load inserts only source versions not yet
   present, in source order, the first day's history and every later day are loaded by the same SQL: on the first
   day all versions are new; on later days only the latest are. This is 149 §5 and ADR-0027 decision 2, without a
   separate first-day script.
2. On the first day every row carries the first load's `load_date`, and the versions are kept apart by their source
   version (149 Rule 2).
3. **A model added later starts on the day it is first built.** For system-versioned tables the history tables
   restore all versions; for the others, the versions seen in earlier extracts are gone unless those extracts are
   replayed. This is why the vault's first day is a choice (§11, choice 2).

## 8. One batch per extract, visible only when whole

1. A batch is one extract: every row of every model built from it carries the same `load_date` and `batch_id`
   (ADR-0031 decision 2).
2. dbt does not build all models in one transaction. Readers are protected by the runner, which publishes the copy
   `published/wwi.duckdb` only after a fully successful `dbt build`, tests included (ADR-0015). A failed build can
   leave a part of a batch in the working warehouse; it is not published and the runner does not move on to the
   next date.
3. **A failed batch is removed before it is retried.** Each generated model has a pre-hook that deletes its own rows
   of the current `batch_id` **written by a dbt run that did not succeed**. *As built (§13 item 5):* every row
   carries `load_run`, the dbt run that wrote it, and every run records whether it succeeded in
   `nsdn_meta.dbt_invocations`; the draft's test on `nsdn_meta.load_log` missed a failed rebuild of a date that had
   succeeded before. So a retry after a
   fix rebuilds the whole batch with the corrected models, and no row of a failed run survives into a published
   one. Rows of a batch that loaded successfully are never deleted, so append-only holds for everything ever
   published.
4. The runner's "rebuild the latest date after a project change" is therefore safe: the latest batch succeeded, so
   nothing is deleted, nothing present is inserted again, and only new models are filled. **A change to how an
   existing model loads does not reach rows already published**; it takes a replay of the kept extracts into a new
   warehouse, under a release note (ADR-0036), and is visible as a diff in release regression (`ARC-OP-30`).
5. Every model must stay safe to run twice on the same extract; a test proves it (§10).

## 9. Staging and landing

1. **Landing stays as it is**: the runner's text tables, one per source table, replaced every load. Nothing in the
   vault reads landing except the generated staging views.
2. **One generated staging view per base table** that a declaration uses: casts each column to its type (§4),
   computes the hash keys of every hub and link the table feeds, `source_ts`, `source_seq` and each satellite's
   `hashdiff`, and unions the history table where there is one. Staging holds no rule of its own beyond these.
3. **Building and testing happen in the cloud workspace first**, on copies of the three kept extracts, with the
   runner's versions (dbt-core 1.12.5, dbt-duckdb 1.11.0, DuckDB 1.5.6) and its landing code. Generated files are
   written into the live project on the author's machine only when they pass there, because the runner takes them
   live within a minute.

## 10. Tests generated with the models

All in the generated `_generated.yml` files or as plain SQL tests; no dbt package (ADR-0015). A failing test fails
the build, and so the batch is not published, unless marked a warning.

1. Hubs and links: hash key unique and not empty; link ends present in their hubs.
2. Satellites: parent key plus source version unique; parent present in its hub.
3. **Every source version in staging is in the audit satellite**, exactly once (the version log is complete).
4. **Same source version, different content** (§6 item 5): error.
5. **Late arrivals** (§6 item 6): warning, with the count; and in the cloud suite, constructed late arrivals with
   restatements, reconstructed at every version.
6. **A mandatory key that arrives empty** (§3 item 5): error.
7. **Twice is the same as once** (§8 item 2): in the cloud test suite, not on every build: load an extract, load it
   again, and compare every table; nothing may change.
8. **Reconstruction**: in the cloud suite, for a sample of keys, the state rebuilt from the satellites at a source
   version equals the source row of that version (149 Rule 10), every column except those declared `load=never`.
9. **A failed batch leaves nothing** (§8 item 3): in the cloud suite, fail a build halfway, change a model, rerun,
   and compare with a clean load of the same extract.

## 11. Choices for the author

*Ruled 2026-11-04 in [ADR-0037](../20_decisions/0037-vault-generator.md): all three as recommended.*

1. **Zero-length versions.** Eleven versions in WWI existed for no time at all (§1 item 4). SQL Server itself leaves
   them out of "as of" queries. *Keep them* (with `source_seq`, §6): the raw vault keeps everything delivered
   (144 §2), and they are evidence of what the source did, such as an update immediately overwritten. *Drop them*:
   simpler ordering, and no business meaning. **Recommended: keep.**
2. **The vault's first day.** The working warehouse has loaded 2016-05-31 to 06-02 with the smoke model only, and
   landing now holds only 06-02. *Start at 06-02*: no action, but the two earlier days' non-versioned states are not
   in the vault. *Replay from 05-31*: the warehouse file is set aside and the runner reloads the three kept extracts
   in order, so the vault starts at 05-31 and the first two daily loads are tested at once, at no cost to the
   source. **Recommended: replay**, done by moving `data/warehouse/` aside (not deleting it) when the generated
   models go live.
3. **`key_case` on the source declaration** (§3 item 4): a field added to the format ruled in ADR-0034, `fold` for
   WWI. **Recommended: add it now**, since it decides the hash of every text key at a PostgreSQL client.

## 12. Not decided here

`deletion-confirmed` in the status-tracking satellites, which needs the conditions of 127 stated as testable rules;
point-in-time and bridge structures of the business vault; access rules per sensitivity class; the second source and
key reconciliation (ADR-0030 decision 2); performance beyond the sandbox: each load compares incoming versions with
whole satellites, which is right for a few million rows and to be revisited for a large client.

## 13. Changes made while building (2026-11-04, session 12)

Found by the first loads and the cloud test suite (`prototypes/vault_generator/test_load.py`); none changes a ruling
of ADR-0037.

1. **Effectivity as one row per change.** Each effectivity satellite is a satellite of the driving hub whose only
   payload is the current link's hash key, loaded by the same pattern as the others (milestone rule: it starts at
   the first version with a link). The information is the same as the draft's pair of rows; the pattern is shared,
   so late arrivals and restatements need no rule of their own, and "ended" is derived from the next row, as "valid
   to" is everywhere (ADR-0027, Consequences).
2. **The end of the source's validity period is kept as delivered text.** SQL Server marks a current row's end
   9999-12-31, which lies beyond DuckDB's `TIMESTAMP_NS` (years 1677 to 2262), and the first load failed on it. The
   end is used only to order ties; its fixed ISO form with seven decimals sorts correctly as text. Start times keep
   all seven decimals as `TIMESTAMP_NS`.
3. **A duplicate is a row identical in every column, its end included.** The first version also ignored the end, and
   so took the three zero-length versions of `Application.People`, whose content equals that of the version that
   replaced them, for duplicates: 2,074 rows delivered, 2,071 staged. A generated test, `…__nothing_dropped`, now
   compares the distinct delivered rows with the staged ones on every build; it fails on the first version.
4. **What the generator covers** is listed in `prototypes/vault_generator/scope.txt`: first four tables (People,
   Customers, Orders, Colors), then all 31 base tables (item 9). A pattern it does not support stops it with a
   message: link satellites, `kept=` other than a bridge's surrogate, a `resolve=` beyond one table of the same
   extract, more than one mapping per hub or link, and keys other than integers and text. Hubs are loaded from their
   own mapping only; that every link end is in its hub is a test.

After the second review on sol, which failed the generated SQL
([XREV](../30_research/notes/XREV_2026-11-04_143-generated-sql_sol.md)):

5. **A failed attempt is known by its run, not its date** (finding 1). Every raw-vault row carries `load_run`, dbt's
   invocation id. Two hooks in `dbt_project.yml` create `nsdn_meta.dbt_invocations` and record, at the end of every
   run, whether all its models and tests succeeded. The pre-hook deletes this batch's rows written by any run not
   recorded as successful. So a failed rebuild of a date that had succeeded (for example a satellite added later and
   first built wrong) leaves nothing once retried, and rows of a successful run are never deleted. `load_run` is the
   one column that differs between two loads of the same extracts; comparisons for release regression leave it out.
6. **Rows within one table are never merged** (finding 2). Only a history row identical in every column, its end
   included, to a row of the current table is taken as the same row delivered twice (149 §5). Two identical rows of
   one table, such as two no-op updates in one transaction, stay two source versions. The `nothing_dropped` test now
   counts exactly that.
7. **The source's closing time of a deleted row is kept** (finding 4). When a key is absent from the current table of
